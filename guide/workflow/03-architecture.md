# 블로그 서비스의 기술과 아키텍처

## 설계 방향

블로그 서비스는 하나의 애플리케이션과 하나의 관계형 데이터베이스로 구성한다. 계정과 글 관리 기능은 애플리케이션 내부의 모듈로 구분하되, 하나의 프로그램으로 배포하는 모듈형 모놀리스 구조를 사용한다.

이 문서의 기술과 구성은 블로그 예시를 위한 설계안이다. 다음 조건을 전제로 한다.

- 첫 번째 배포 후 3개월 시점에 전체 사용자 1,000명과 동시 사용자 50명을 예상한다.
- 성능 검증은 동시 사용자 100명에서 수행하며, 동작별 성공 건의 p95 완료 시간 2초 이하를 기준으로 한다.
- 각 동작의 월간 가용성 목표는 99.5% 이상이다.
- 첫 배포는 단일 지역에서 운영하며, 여러 서비스를 따로 배포하고 관리하는 구성은 사용하지 않는다.
- 공개 글의 작성·수정·삭제 결과는 처리 완료 후 조회에 반영되어야 한다.

계정과 글 관리에 필요한 처리를 한 애플리케이션 안에 두어 배포와 요청 처리를 단순하게 유지한다. 별도의 캐시, 메시지 브로커, 검색 서버는 도입하지 않는다.

## 시스템 구성 요약

```text
클라이언트
    |
    | HTTPS
    v
블로그 애플리케이션
    |
    | SQL
    v
PostgreSQL
```

- **클라이언트**: 회원가입, 로그인, 글 작성·조회·수정·삭제를 요청하고 결과를 표시한다. 구체적인 화면과 클라이언트 기술은 이 서버 구성에 포함하지 않는다.
- **블로그 애플리케이션**: HTTPS 요청 수신, 입력 검증, 사용자 식별, 권한 확인, 계정·글 관리와 응답 생성을 담당한다.
- **PostgreSQL**: 회원 계정, 로그인 세션, 글을 저장하는 기준 저장소다. 글 조회는 변경이 반영된 동일한 데이터베이스에서 수행한다.

애플리케이션 내부는 HTTP 요청·응답 처리, 계정·인증, 글 관리, 데이터 저장 접근의 책임으로 구분한다. 계정·인증 모듈은 현재 회원 식별을 담당하고, 글 관리 모듈은 작성·수정·삭제에 필요한 소유권 규칙을 적용한다.

쓰기 요청은 필요한 데이터 변경이 완료된 뒤 성공 결과를 제공한다. 처리 실패 시 일부 변경만 남지 않도록 트랜잭션 경계를 정한다. 공개 결과 반영을 별도의 비동기 작업으로 미루지 않는다.

첫 배포에서는 Linux 호스트에서 Docker로 애플리케이션 컨테이너 1개와 데이터베이스 컨테이너 1개를 실행한다. 단일 인스턴스의 장애로 서비스가 중단될 수 있으므로, 재시작·복구 절차와 실제 가용성 측정을 통해 운영 목표의 충족 여부를 확인한다. 예상 규모만으로 성능이나 가용성 충족을 단정하지 않는다.

## 사용 기술 요약

| 영역 | 기술·버전 | 용도 |
| --- | --- | --- |
| 서버 언어 | Go 1.27.3 | 블로그 애플리케이션 구현 |
| HTTP 처리 | Go 1.27.3 표준 라이브러리 `net/http` | HTTPS 요청 수신과 API 응답 처리 |
| 데이터베이스 | PostgreSQL 18.6 | 회원, 로그인 세션, 글의 영속 저장 |
| 호스트 운영체제 | Linux | Docker 실행 호스트 |
| 서버 실행 환경 | Docker | 애플리케이션과 데이터베이스를 각각 컨테이너로 실행 |

별도의 웹 프레임워크 없이 표준 HTTP 기능으로 시작한다. 데이터 저장은 관계형 데이터베이스 한곳으로 모아 계정 고유성과 글 소유권, 데이터 변경의 무결성을 관리한다.

로그인은 서버가 관리하는 세션 방식으로 구성한다. 클라이언트는 쿠키로 세션 식별자를 전달하고, 서버가 세션의 유효성과 회원을 확인한다. 세션 수명과 쿠키 보안 속성, 비밀번호 보호 방식, 데이터베이스 접근 라이브러리와 실행 환경의 세부 버전은 상세 설계에서 구체화한다.

## 상세 설계 문서 안내

상세 설계는 `03-architecture/` 폴더에 분리할 예정이며, 현재는 이 대표 문서만 작성한다.

상세 설계에서 다룰 주제는 다음과 같다.

- **제약조건과 운영 기준**: 서버 자원, 예산, 배포 환경, 부하 구성, 성능·가용성 검증 조건.
- **기술 선택**: 사용 기술과 버전의 선택 이유, 검토한 대안과 트레이드오프.
- **시스템과 모듈 경계**: 구성요소별 책임, 내부 의존 방향, 요청과 데이터의 흐름, 트랜잭션과 장애 경계.
- **인증과 보안**: 비밀번호 보호, 세션 발급·만료·폐기, 쿠키 보안, 권한 확인과 HTTPS 구성.
- **저장과 운영**: 데이터 무결성, 동시 변경 처리, 마이그레이션, 배포·복구, 백업과 관측 방식.

상세 문서를 작성하면 이 섹션에 실제 문서의 경로와 읽는 순서를 정리한다. 각 설계 항목의 기준은 담당 상세 문서에 두고, 이 대표 문서는 전체 구성과 주요 선택의 요약으로 유지한다.
