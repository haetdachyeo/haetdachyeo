# ブログサービスの技術とアーキテクチャ

## 設計方針

ブログの設計例：**モジュラーモノリス**、アプリケーション1つ・リレーショナルDB1つ。機能別にモジュールを分け、単一プログラムとしてデプロイ。

| 項目 | 前提・目標 |
| --- | --- |
| 想定規模 | 初回リリースから3か月後、全体1,000人・同時50人 |
| 性能検証 | 同時ユーザー100人、操作別の成功リクエストのp95完了時間2秒以下 |
| 月間可用性 | 操作別99.5%以上 |
| 運用構成 | 単一リージョン、サービス別のデプロイ・管理なし |
| 変更反映 | 変更成功レスポンス後に開始した取得に反映 |

デプロイ・リクエスト処理を単純化。独立したキャッシュ・メッセージブローカー・検索サーバーは未導入。

## システム構成の概要

```text
クライアント
    |
    | HTTPS
    v
ブログアプリケーション
    |
    | SQL
    v
PostgreSQL
```

| 構成要素 | 責務 |
| --- | --- |
| クライアント | リクエスト生成・結果表示。画面・クライアント技術は別途決定 |
| アプリケーション | HTTPS受信・入力検証・認証・権限確認・業務処理・レスポンス生成 |
| PostgreSQL | サービスデータの基準ストア。閲覧・変更に同じDBを使用 |

内部の責務：リクエスト・レスポンス / 業務処理 / データアクセス / 技術連携。
機能別の業務ルールは担当Serviceが所有。具体的な機能・API・ドメインの一覧は機能仕様で管理。
内部設計：機能別の区分にController・Service・Repositoryの役割を適用。HTTP処理はController・Router・Middlewareが担当し、Serviceの保存契約と具体的な実装を実行開始点で接続。

- **書き込み**：変更完了後に成功レスポンス。失敗時の部分変更を防ぎ、トランザクション境界を定義。
- **公開反映**：別の非同期処理に先送りしない。
- **初回リリース**：LinuxホストのDockerで、アプリケーション・DBコンテナ各1つ。
- **障害**：単一インスタンスの停止リスク。再起動・復旧手順と実測可用性で検証。想定規模だけで目標達成を断定しない。

## 使用技術の概要

| 領域 | 技術・バージョン | 用途 |
| --- | --- | --- |
| サーバー言語 | Go 1.27.3 | ブログの実装 |
| HTTP処理 | Go 1.27.3標準 `net/http` | HTTPS受信・APIレスポンス |
| データベース | PostgreSQL 18.6 | サービスデータの永続保存 |
| ホストOS | Linux | Docker実行ホスト |
| サーバー実行環境 | Docker | アプリケーション・DBを別コンテナで実行 |

- **HTTP**：別のWebフレームワークなしで標準機能を使用。
- **保存**：単一リレーショナルDBで、一意性・参照制約・変更の整合性を管理。
- **ログイン**：サーバーセッション。Cookieで識別子を送信し、PostgreSQLのセッションの有効性・会員を確認。

詳細化対象：セッションの有効期間・Cookieのセキュリティ・パスワード保護・DBアクセスライブラリ・実行環境の詳細バージョン。
