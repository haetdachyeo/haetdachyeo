# ブログサービスの技術とアーキテクチャ

## 設計方針

ブログサービスは、1つのアプリケーションと1つのリレーショナルデータベースで構成する。アカウント管理と記事管理はアプリケーション内部のモジュールとして分離し、1つのプログラムとしてデプロイするモジュラーモノリス構成を採用する。

この文書の技術と構成は、ブログの例に対する設計案である。以下の条件を前提とする。

- 初回リリースから3か月後の時点で、総ユーザー数1,000人、同時ユーザー数50人を想定する。
- 性能検証は同時ユーザー100人で実施し、操作ごとに成功したリクエストのp95完了時間が2秒以下であることを基準とする。
- 各操作の月間可用性目標は99.5%以上とする。
- 初回リリースは単一リージョンで運用し、複数のサービスを個別にデプロイ・管理する構成は採用しない。
- 公開記事の作成・編集・削除の結果は、処理完了後の閲覧に反映されなければならない。

アカウント管理と記事管理に必要な処理を1つのアプリケーションにまとめ、デプロイとリクエスト処理をシンプルに保つ。独立したキャッシュ、メッセージブローカー、検索サーバーは導入しない。

## システム構成の概要

```text
クライアント
    |
    | HTTPS
    v
ブログアプリケーション
    |
    | SQL
    v
PostgreSQL
```

- **クライアント**：会員登録、ログイン、記事の作成・取得・編集・削除をリクエストし、結果を表示する。具体的な画面とクライアント技術は、このサーバー構成に含めない。
- **ブログアプリケーション**：HTTPSリクエストの受信、入力検証、ユーザーの識別、権限確認、アカウント・記事管理、レスポンスの生成を担当する。
- **PostgreSQL**：会員アカウント、ログインセッション、記事を保存する基準となるデータストアである。記事の取得には、変更が反映された同じデータベースを使用する。

アプリケーション内部では、HTTPリクエスト・レスポンス処理、アカウント・認証、記事管理、データアクセスの責任を分離する。アカウント・認証モジュールは現在の会員を識別し、記事管理モジュールは作成・編集・削除に必要な所有権ルールを適用する。

書き込みリクエストでは、必要なデータ変更が完了してから成功結果を返す。処理失敗時に一部の変更だけが残らないよう、トランザクションの境界を定める。公開結果への反映を別の非同期処理に先送りしない。

初回リリースでは、Linuxホスト上のDockerでアプリケーションコンテナ1つとデータベースコンテナ1つを実行する。単一インスタンスの障害によってサービスが中断する可能性があるため、再起動・復旧手順と実際の可用性測定を通じて運用目標を満たしているか確認する。想定規模だけで性能や可用性の達成を断定しない。

## 使用技術の概要

| 領域 | 技術・バージョン | 用途 |
| --- | --- | --- |
| サーバー言語 | Go 1.27.3 | ブログアプリケーションの実装 |
| HTTP処理 | Go 1.27.3標準ライブラリ `net/http` | HTTPSリクエストの受信とAPIレスポンスの処理 |
| データベース | PostgreSQL 18.6 | 会員、ログインセッション、記事の永続保存 |
| ホストOS | Linux | Dockerを実行するホスト |
| サーバー実行環境 | Docker | アプリケーションとデータベースを個別のコンテナで実行 |

独立したWebフレームワークを導入せず、標準のHTTP機能から始める。データ保存先を1つのリレーショナルデータベースに集約し、アカウントの一意性、記事の所有権、データ変更の整合性を管理する。

ログインにはサーバー管理のセッション方式を採用する。クライアントはCookieでセッション識別子を送信し、サーバーがセッションの有効性と会員を確認する。セッションの有効期間、Cookieのセキュリティ属性、パスワードの保護方式、データベースアクセスライブラリ、実行環境の詳細バージョンは詳細設計で具体化する。

## 詳細設計文書の案内

詳細設計は`03-architecture/`フォルダーに主題ごとに整理する。まず設計の前提と技術選定を読み、その後に各主題の詳細設計へ進む。

- [ブログサービスの設計の前提と技術選定](03-architecture/01-design-decisions.ja.md)：利用・運用条件、技術と構造の選定根拠、検証と判断を見直す基準。
- [設計の前提と技術選定の記入用テンプレート（韓国語）](03-architecture/01-design-decisions.example.md)：想定利用状況、制約条件と品質目標、選定理由・代替案・トレードオフ、検証と判断を見直す基準。

詳細設計で扱う主題は以下のとおりである。

- **制約条件と運用基準**：サーバーリソース、予算、デプロイ環境、負荷構成、性能・可用性の検証条件。
- **技術選定**：使用技術とバージョンの選定理由、検討した代替案、トレードオフ。
- **システムとモジュールの境界**：構成要素ごとの責任、内部の依存方向、リクエストとデータの流れ、トランザクションと障害の境界。
- **認証とセキュリティ**：パスワード保護、セッションの発行・有効期限・無効化、Cookieのセキュリティ、権限確認、HTTPS構成。
- **保存と運用**：データ整合性、同時変更の処理、マイグレーション、デプロイ・復旧、バックアップ、オブザーバビリティ。

詳細文書を作成したら、このセクションに実際の文書のパスと読む順序を記載する。各設計項目の基準は担当する詳細文書に置き、この代表文書は全体構成と主要な選択の要約として維持する。
