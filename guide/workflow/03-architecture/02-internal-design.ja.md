# ブログサービスの内部設計

- 設計の前提: [設計の前提と技術選定](01-design-decisions.ja.md)。初回リリースから3か月後・全体1,000人・同時50人・開発/運用1人

## 設計方式

### デプロイ構造: モジュラーモノリス、単一Goプログラム

理由: 開発・運用1人で管理するデプロイ単位を1つに保つために選択。

### 内部設計: 機能別の分離、Controller・Service・Repositoryの役割を適用

理由: 業務ルールをHTTP・SQLの変更から分離。リクエスト処理に業務・SQLを統合するとルールが分散し、検証負担が増えると判断。役割別の形式変換・インターフェース同期のコストは受け入れる。

### 機能モジュール: 機能別の独立モジュール

理由: データ所有・変更範囲を区別するために選択。機能区分のない層別共通フォルダーは、この境界を示しにくいため不採用。

### リクエスト処理: 同期処理。変更確定後に成功レスポンス

理由: 変更完了と後続の取得への反映時点を単純に対応させるために選択。

### モジュール接続: 関数・メソッドの直接呼び出し

理由: 単一プログラム内の呼び出しを直接追跡し、独立した配送機構の運用負担を避けるために選択。

### 実装言語: Go 1.27.3

理由: 開発・運用者のGoスキルと単一サーバープログラムのデプロイに合わせて選択。

### リクエスト処理技術: Go 1.27.3標準`net/http`

理由: 現在の機能は別のWebフレームワークを使わず、標準HTTP機能で処理できると判断。

### データベース: PostgreSQL 18.6、単一の基準ストア

理由: リレーショナルデータの一意性・参照制約とトランザクションを1つのストアで管理するために選択。

### 認証方式: PostgreSQLに保存するサーバーセッション

理由: 現在のログイン状態をサーバーで確認・無効化し、独立したセッションストアの運用を避けるために選択。

### 実行環境: Linuxホスト、Docker

理由: プロジェクトのLinux・Docker実行条件に従い、アプリケーション・DBの実行単位を分けるために選択。

### 未導入の構成: 独立ドメイン層・汎用リポジトリ・共通トランザクション管理・イベント/コマンドバス・キャッシュ・非同期の参照モデル

理由: 現在の機能に対して抽象化・接続・失敗追跡のコストが大きいと判断。必要な責務分離だけを維持するために未導入。

## 構成と責務

| 構成要素 | 役割・担当範囲 | 境界 |
| --- | --- | --- |
| Controller・Router・Middleware | 外部リクエスト解釈・形式検証、Service呼び出し、レスポンス変換 | 業務ルール・SQL処理は禁止 |
| Service | 業務ルール・権限・処理単位、モデル・入出力型・契約を所有 | HTTPオブジェクト・SQL・DB接続の参照は禁止 |
| Repository実装 | 保存契約の実装、クエリ・制約結果の変換、原子性の保証 | レスポンス決定・Service呼び出し・他モジュールのデータの任意変更は禁止 |
| 外部機能の実装 | Serviceが定義した技術連携契約の実装 | 具体的な技術・ライブラリをServiceに公開しない |
| 実行開始点 | 設定検証、DB・実装の生成と注入、起動・終了 | リクエストごとの業務ルール配置は禁止 |

## 依存関係

- ソースコード参照: Controller → Service、保存・外部機能の実装 → Serviceの契約
- 実行時の呼び出し: Service → 注入された実装。グローバルなDB・セッション・サービスの取得は不使用
- 構成要素の組み立て: 実行開始点で具体的な実装を生成・接続
- 許可・禁止する依存: Serviceは標準ライブラリ・自身の業務型・契約を使用。HTTP・DB実装・他の業務モジュールの直接参照と循環依存は禁止
- 境界の契約: 利用するServiceモジュールが契約を所有。業務型・値・条件・結果・エラーを渡し、SQL・DB行・トランザクションオブジェクトは隠蔽
- 業務ルールの表現: モジュール別の関数・型。全関数のインターフェース化・同じ層数の強制なし

## フォルダー構成

| パス | 役割 |
| --- | --- |
| `cmd/` | 実行開始点・実装の接続 |
| `internal/<module>/` | 機能別Service・モデル・契約の配置パターン |
| `internal/transport/` | 外部リクエスト・レスポンス処理 |
| `internal/storage/` | Repository実装 |
| `internal/adapter/` | 外部機能の実装 |
| `internal/config/` | 実行設定の読み込み・検証 |
| `migrations/` | DBスキーマ変更 |
| `deploy/` | デプロイ設定 |

`<module>`は機能名に置き換えるパターン。具体的な機能・ファイルの一覧は機能仕様で管理。

- 実行開始点：`cmd/`
- テスト配置：対象パッケージ
- 統合テスト配置：`internal/storage/`、保存契約の検証

## 主要ルール

### 基本フロー

- 確定値: Controller → Service → Repository → 結果 → レスポンス。取得・変更は同じ業務境界・基準DBを使用

### 入力検証

- 確定値: Controllerはリクエスト形式、Serviceは業務入力ルールを検証

### 権限確認

- 確定値: 認証済み呼び出し元のコンテキストをServiceに渡し、Serviceで業務権限を判断

### データ整合性

- 確定値: 変更成功レスポンス後に開始した取得に変更を反映。独立したキャッシュ・非同期の参照モデルは不使用

### エラー

- 確定値: 保存・外部機能の実装で技術エラーを業務エラーに変換し、Controllerで外部レスポンスに変換。内部エラー原文の公開は禁止

### 原子性

- 確定値: Serviceがまとめて成功・失敗する単位を契約に明記。Repositoryが単一SQLまたはトランザクションで保証。複数呼び出しを全体の原子性とみなさない

### 失敗・キャンセル

- 確定値: 保存完了確認前の成功・部分変更の成功扱いは禁止。失敗・結果不確実時の変更の自動再実行は禁止。キャンセル・期限を保存処理まで伝達するが、確定済み変更はキャンセル・応答送信失敗で取り消さない

### 構造の見直し条件

- 確定値: 責務・依存方向・デプロイ単位が変わる場合に見直す。モジュール間の原子的変更・複雑なルール・独立デプロイの要求を含む。API追加だけで構造文書を変更せず、将来の可能性だけで層を追加しない

### 確認方法

- 確定値: 禁止・循環依存を検査。HTTP・実DBなしでServiceのルール・失敗伝達を検証。実DBで保存契約・原子性・エラー変換・変更反映を検証

### 詳細仕様

- 確定値: 具体的な機能・データ・APIルールは[機能別の動作ルール](../02-scope.ja.md#機能別の動作ルール)で管理。新機能には既存のモジュール配置パターンを適用。具体的なインターフェース・セキュリティ・デプロイ・復旧手順は後続の設計対象

- 検証状態：文書設計のみ。実装・依存関係検査・業務テスト・DB統合テストは未実施。
- 実装準備：未完了。機能・API・DB・セキュリティ・運用の詳細仕様に未確定事項あり。
