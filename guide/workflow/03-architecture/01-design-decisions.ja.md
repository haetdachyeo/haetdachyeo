# ブログサービスの設計の前提と技術選定

## 設計の前提

対象：会員の記事作成・管理、訪問者の公開記事閲覧。想定規模は設計基準。

| 項目 | 設計の前提 |
| --- | --- |
| 想定時点 | 初回リリースから3か月後 |
| 総ユーザー数 | 会員・訪問者合計1,000人 |
| 同時ユーザー数 | 50人 |
| 主な利用 | 公開記事の一覧・詳細閲覧 |
| 操作比率 | 取得90%、アカウント処理・記事変更10% |
| 平均リクエスト量 | 1件/秒 = 利用中のユーザー10人 × 1件/10秒 |
| 混雑時リクエスト量 | 10件/秒 = 利用中のユーザー50人 × 1件/5秒 |
| 瞬間リクエスト量 | 50件/秒 = 利用中のユーザー50人 × 1件/秒 |
| 記事増加量 | 100件/日 |
| 記事平均サイズ | タイトル・本文合計10KiB |
| データ増加量 | タイトル・本文約1MiB/日。オンライン保存の増加予算2GiB/年：会員・セッション・メタデータ・インデックス込み |
| クライアント | CookieベースのWebブラウザー。画面技術は別途決定 |
| 運用地域 | 韓国、単一地域 |

リクエスト頻度・操作比率・データ増加量・運用地域：設計例の仮定。記事平均サイズ：容量算定用、入力上限ではない。

## 制約条件と品質目標

### 実行環境と運用条件

| 項目 | 条件 |
| --- | --- |
| ホストOS | Linux |
| 実行方式 | Docker、アプリケーション・PostgreSQLは別コンテナ |
| 初期配置 | ホスト1台、アプリケーション・DBコンテナ各1つ |
| ホストリソース | 4 vCPU、RAM 8GiB、SSD 100GiB |
| アプリケーション上限 | CPU 1個相当、RAM 1GiB |
| DB上限 | CPU 2個相当、RAM 4GiB |
| リソース余裕 | OS・Docker・運用作業用 |
| 月間予算 | 10万ウォン以内。サーバー・ストレージ・バックアップ・ネットワーク込み |
| 開発・運用人数 | 1人 |
| 人員の前提 | Go・SQL・Linux・Dockerの基本スキル、定期運用は週2時間 |
| 運用方式 | 自動ヘルスチェック・障害通知、受信時に対応。常時の手動監視なし |

固定条件：Linux・Docker。設計例の仮定：リソース・予算・人員。商品見積もり・処理能力の実測ではない。
構成要素追加時はデプロイ・バックアップ・監視コストを反映。

### 品質目標

対象：会員登録・ログイン・ログアウト・記事作成・公開一覧・公開詳細・編集・完全削除、計8操作。

| 項目 | 基準 |
| --- | --- |
| 応答時間 | 同時ユーザー100人、操作別の成功リクエストのp95完了時間2秒以下 |
| 測定区間 | サービスのリクエスト受信から結果が利用可能になるまで |
| 測定対象外 | クライアント側のネットワーク転送・描画・ユーザーの思考時間 |
| 月間可用性 | 操作別99.5%以上。有効かつ権限のあるリクエストに正常結果を提供できる時間 / 全体時間 |
| 正常な拒否 | 入力・権限エラーの正常な拒否は利用不能時間から除外 |
| 月間停止上限 | 全体時間の0.5%。30日換算216分、デプロイ停止を含む |
| 復旧時間 | サービス停止発生から60分以内 |
| データ復旧時点 | DB全体の復旧：最大24時間前の時点を確保 |
| 変更反映 | 作成・編集・削除の成功レスポンス後に開始した取得に変更を反映 |
| 失敗時の整合性 | 部分変更結果の成功扱いを禁止 |

月間停止上限は個別の復旧時間とは別に判定。単一ホストの通知・バックアップ・復旧目標は復旧訓練で検証。

### セキュリティ条件

- 認証情報・記事変更リクエスト：HTTPS。
- パスワード：平文保存・ログ記録禁止。
- 記事編集・削除：サーバーで現在の会員と作成者の所有権を確認。
- DB：クライアントの直接アクセス・公開サービス提供禁止。
- DB認証情報・セッション識別子：ソースコード・通常のリクエストログへの露出禁止。

詳細化：パスワード・セッション・Cookieのセキュリティ / ネットワークアクセス / 秘密情報の注入。担当：セキュリティ・システム・運用設計。

## 技術と構造の選択

### モジュラーモノリス

- **必要性**：機能別の責任分離、少人数でのデプロイ・障害管理。
- **選択**：アカウント・認証 / 記事管理 / HTTP処理 / データアクセスをモジュール分離。単一アプリケーションでデプロイ。
- **条件**：小規模利用、1人運用、予算制限。
- **理由**：内部呼び出し・単一DBトランザクション。サービス間通信・個別デプロイ管理は不要。
- **代替案の除外**：マイクロサービスは契約・デプロイ・障害管理の負担。モジュール未分離は変更境界が不明確。
- **コスト**：デプロイ・プロセス障害が全体に影響。モジュール別の独立デプロイ・個別拡張不可。

### Goと標準HTTP処理

- **必要性**：HTTP API・アカウント・記事管理の実装。
- **選択**：Go 1.27.3、標準 `net/http`のサーバー・ルーティング。
- **条件**：基本的なアカウント・公開記事機能、運用者のGoスキル。
- **理由**：単一サーバープログラム、標準HTTP機能の活用、別のフレームワーク規約なし。
- **代替案の除外**：Go Webフレームワークは必須要件なし。他言語は現在の人員・実行環境を変更する必要性なし。
- **コスト**：エラー・入力検証・認証の連携を直接設計。外部ライブラリの使用は許可。

### PostgreSQL

- **必要性**：会員・セッション・記事の永続保存、一意性・所有関係・変更整合性。
- **選択**：PostgreSQL 18.6を単一の基準ストアに採用。閲覧・変更に同じDBを使用。
- **条件**：リレーショナルデータ、変更成功後の最新結果閲覧。
- **理由**：一意性・参照制約、関連変更のトランザクション処理。
- **代替案の除外**：SQLiteではなく独立コンテナ型PostgreSQLを採用。ドキュメント型ストアは必須要件なし。複数ストアは整合性・復旧の境界が増加。
- **コスト**：DBプロセス・接続・マイグレーション・バックアップの運用。単一DB障害が全体に影響。

### Linux・Dockerの単一ホスト配置

- **必要性**：実行環境の分離、同一構成でのデプロイ。
- **選択**：Linuxホスト1台、アプリケーション・DBは別Dockerコンテナ。DBデータはコンテナ交換と分離して保持。
- **条件**：Linux・Docker固定、リソース上限・1人運用・予算制限。
- **理由**：単一ホスト維持、実行・交換単位の分離。
- **代替案の除外**：直接インストールはコンテナ配置条件に不適合。複数ホストのオーケストレーション・DB冗長化は初回リリースで不採用。
- **コスト**：ホスト障害・リソース競合の同時影響。高可用性の保証なし。

システム・デプロイの詳細化：Linuxディストリビューション、Dockerバージョン、イメージ固定、ネットワーク・ボリューム設定。

### DB保存型サーバーセッション

- **必要性**：リクエストごとの会員識別、ログアウトした利用状態の会員専用操作の遮断。
- **選択**：Cookieでセッション識別子を送信、PostgreSQLのセッションを確認。アカウント情報・有効期間・有効性はサーバー管理。
- **条件**：ブラウザー利用、現在の利用状態のログアウト、単一ストア。
- **理由**：サーバーでログインの有効性・無効化を管理。別のセッションストアは不要。
- **代替案の除外**：自己完結型トークンはログアウト・無効化ルールの追加が必要。Redisセッションはストア運用の負担増。
- **コスト**：セッション照会・期限切れデータ整理、Cookieのセキュリティ・リクエスト偽造対策。

### 独立したキャッシュ・メッセージブローカー・検索サーバーの未導入

- **必要性**：実装・運用構成の最小化。
- **選択**：アカウント・記事処理はアプリケーション・PostgreSQLに限定。
- **条件**：検索・メディアアップロード対象外、公開記事変更の即時反映。
- **理由**：非同期の公開更新・キャッシュ無効化の境界なしに単一ストアを使用。
- **代替案の保留**：キャッシュによる閲覧負荷分散・ブローカーによる処理分離・検索サーバーは必要性の確認後に再検討。
- **コスト**：閲覧・変更負荷の集中。目標未達時はクエリ・インデックス・接続・リソース配置から確認。

## 検証と見直し基準

### 検証環境と負荷

| 項目 | 条件 |
| --- | --- |
| サーバー | 別Linuxホスト、本番と同じリソース・イメージ・コンテナ上限 |
| 負荷生成器 | サーバーとは別ホスト |
| 初期データ | 合成アカウント1,000件、公開記事100,000件、タイトル・本文平均合計10KiB |
| データ規模の根拠 | 3か月の想定約9,000件を超える累積データ検証 |
| 継続負荷 | 仮想ユーザー100人 × 平均1件/5秒 = 20件/秒 |
| ログイン必須操作 | 有効なアカウント・セッションを使用、編集・削除は本人の記事 |
| 会員登録 | 未登録メールアドレスを使用 |
| データ変化 | 記事作成・削除を測定結果と併記 |
| 成功サンプル | 操作別に最低1,000件 |
| p95計算 | 操作別の成功完了時間の昇順、`ceil(0.95 × サンプル数)`番目の値 |
| 予期しない失敗 | 有効かつ権限のあるリクエストの失敗を機能・安定性の問題として別途記録 |
| 集中リクエスト | ログインユーザー100人、共通の開始シグナル、各自有効なリクエスト1件を同時送信 |
| 集中リクエスト判定 | エラー・リソース飽和を別途確認。継続負荷のp95と合算禁止 |

混合負荷：公開一覧45%、公開詳細45%、ログイン3%、ログアウト2%、記事作成2%、編集2%、会員登録0.5%、完全削除0.5%。

検証対象8操作とAPIの数・パスは別。リクエスト構成はAPI設計後に確定。

### リソース・コスト・復旧検証

| 項目 | 判定基準 |
| --- | --- |
| 負荷安定性 | メモリ不足による終了・コンテナ再起動なし |
| CPU | 継続負荷区間のホスト平均使用率70%以下 |
| ディスク | 使用量・増加量から3か月以内に使用率70%到達を予測した場合、容量・保持方針を見直し |
| コスト | サーバー・ストレージ・バックアップ・ネットワーク合計、月10万ウォン以内 |
| 復旧訓練 | アプリケーション停止・ホスト喪失を個別検証。停止から60分以内に復旧、復旧時点は最大24時間前 |
| バックアップ復元 | アカウント・記事・セッションの整合性、完全削除記事の再公開防止 |
| 月間可用性 | 本番観測・操作別に計算。負荷・復旧試験のみの達成判定は禁止 |

保持・復元ルール：保存・運用の詳細設計で定義。

### 選択を見直す条件

| 条件変更・未達項目 | 見直し対象 |
| --- | --- |
| 想定の総ユーザー数・同時ユーザー数を超える計画 | リクエスト量・データ量・検証負荷の再算定 |
| 応答時間未達 | リクエスト処理・クエリ・インデックス・接続・リソースを確認後、インスタンス追加・構造変更 |
| 可用性・復旧目標未達 | 単一ホスト配置、バックアップ・復旧運用 |
| 人員・予算変更、モジュールの独立デプロイ要件 | デプロイ単位・責任境界 |
| 技術バージョンのセキュリティ・保守問題 | バージョン変更・互換性検証 |
| キャッシュ・非同期・検索を必要とする機能追加 | 機能・負荷を根拠に構成要素の導入判断 |

検証：計画のみ。実装・負荷・コスト・復旧の検証は未実施。
決定変更：該当項目を直接修正し、代表文書の要約を同期。
