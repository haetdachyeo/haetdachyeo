# 블로그 서비스의 내부 설계 방식

- 설계 전제: [설계 전제와 기술 선택](01-design-decisions.md). 첫 배포 후 3개월·전체 1,000명·동시 50명·개발/운영 1명

## 설계 방식

### 배포 구조: 모듈형 모놀리스, 단일 Go 프로그램

이유: 개발·운영 1명이 관리할 배포 단위를 하나로 유지하기 위해 선택.

### 내부 설계 방식: 기능별 분리, Controller·Service·Repository 역할 적용

이유: 업무 규칙을 HTTP·SQL 변경과 분리. 요청 함수에 업무·SQL을 합치면 규칙이 흩어져 검증 부담이 커진다고 판단. 역할별 표현 변환·인터페이스 동기화 비용은 감수.

### 기능 모듈: 기능별 독립 모듈

이유: 데이터 소유·변경 범위를 구분하기 위해 선택. 기능 구분 없는 계층별 공통 폴더는 이 경계를 드러내기 어려워 미채택.

### 요청 처리 방식: 동기 처리. 변경 확정 후 성공 응답

이유: 변경 완료와 후속 조회의 반영 시점을 단순하게 맞추기 위해 선택.

### 모듈 연결 방식: 직접 함수·메서드 호출

이유: 단일 프로그램에서 호출 관계를 직접 추적하고, 별도 전달 체계의 운영 부담을 줄이기 위해 선택.

### 구현 언어: Go 1.27.3

이유: 개발·운영자의 Go 역량과 단일 서버 프로그램 배포에 맞춰 선택.

### 요청 처리 기술: Go 1.27.3 표준 `net/http`

이유: 현재 기능은 별도 웹 프레임워크 없이 표준 HTTP 기능으로 처리할 수 있다고 판단.

### 데이터베이스: PostgreSQL 18.6, 단일 기준 저장소

이유: 관계형 데이터의 고유성·참조 제약과 트랜잭션을 한 저장소에서 관리하기 위해 선택.

### 인증 방식: PostgreSQL에 저장하는 서버 세션

이유: 현재 로그인 상태를 서버에서 확인·폐기하고, 별도 세션 저장소 운영을 피하기 위해 선택.

### 실행 환경: Linux 호스트, Docker

이유: 프로젝트의 Linux·Docker 실행 조건을 따르고, 애플리케이션·DB의 실행 단위를 나누기 위해 선택.

### 미도입 구성: 별도 도메인 계층·범용 저장소·공통 트랜잭션 관리자·이벤트/명령 버스·캐시·비동기 조회 모델

이유: 현재 기능 대비 추상화·연결·실패 추적 비용이 크다고 판단. 필요한 책임 분리만 유지하기 위해 미도입.

## 구성과 책임

| 구성요소 | 역할·담당 범위 | 경계 |
| --- | --- | --- |
| Controller·Router·Middleware | 외부 요청 해석·형식 검증, Service 호출, 응답 변환 | 업무 규칙·SQL 처리 금지 |
| Service | 업무 규칙·권한·처리 단위, 모델·입출력 타입·계약 소유 | HTTP 객체·SQL·DB 연결 참조 금지 |
| Repository 구현 | 저장 계약 구현, 쿼리·제약 결과 변환, 원자성 보장 | 응답 결정·Service 호출·다른 모듈 데이터의 임의 변경 금지 |
| 외부 기능 구현 | Service가 정의한 기술 연동 계약 구현 | 구체 기술·라이브러리를 Service에 노출하지 않음 |
| 실행 진입점 | 설정 검증, DB·구현 생성·주입, 시작·종료 | 요청별 업무 규칙 배치 금지 |

## 의존 관계

- 소스 코드 참조: Controller → Service, 저장소·외부 기능 구현 → Service의 계약
- 실행 시 호출: Service → 주입된 구현. 전역 DB·세션·서비스 조회 미사용
- 구성요소 조립: 실행 진입점에서 구체 구현 생성·연결
- 허용·금지 의존: Service는 표준 라이브러리·자기 업무 타입·계약 사용. HTTP·DB 구현·다른 업무 모듈의 직접 참조와 순환 의존 금지
- 경계 계약: 사용하는 Service 모듈이 계약 소유. 업무 타입·값·조건·결과·오류 전달. SQL·DB 행·트랜잭션 객체 숨김
- 업무 규칙 표현: 모듈별 함수·타입. 모든 함수의 인터페이스화·동일한 계층 수 강제 없음

## 폴더 구조

| 경로 | 역할 |
| --- | --- |
| `cmd/` | 실행 진입점·구현 연결 |
| `internal/<module>/` | 기능별 Service·모델·계약의 배치 패턴 |
| `internal/transport/` | 외부 요청·응답 처리 |
| `internal/storage/` | Repository 구현 |
| `internal/adapter/` | 외부 기능 구현 |
| `internal/config/` | 실행 설정 읽기·검증 |
| `migrations/` | DB 스키마 변경 |
| `deploy/` | 배포 설정 |

`<module>`은 기능명으로 교체하는 패턴. 구체적인 기능·파일 목록은 기능 사양에서 관리.

- 실행 진입점: `cmd/`
- 테스트 위치: 대상 패키지
- 통합 테스트 위치: `internal/storage/`, 저장 계약 검증

## 주요 규칙

### 기본 흐름

- 확정값: Controller → Service → Repository → 결과 → 응답. 읽기·쓰기는 같은 업무 경계·기준 DB 사용

### 입력 검증

- 확정값: Controller는 요청 형식, Service는 업무 입력 규칙 검증

### 권한 검사

- 확정값: 인증된 호출자 문맥을 Service에 전달하고, Service에서 업무 권한 판단

### 데이터 일관성

- 확정값: 변경 성공 응답 후 시작한 조회에 변경 반영. 별도 캐시·비동기 조회 모델 미사용

### 오류

- 확정값: 저장소·외부 기능 구현에서 기술 오류를 업무 오류로 변환, Controller에서 외부 응답으로 변환. 내부 오류 원문 노출 금지

### 원자성

- 확정값: Service가 함께 성공·실패할 단위를 계약에 명시. Repository가 단일 SQL 또는 트랜잭션으로 보장. 여러 호출을 전체 원자성으로 간주하지 않음

### 실패·취소

- 확정값: 저장 완료 확인 전 성공·부분 변경의 성공 처리 금지. 실패·결과 불확실 시 자동 변경 재실행 금지. 취소·기한은 저장소까지 전달하며, 확정된 변경은 취소·응답 전송 실패로 되돌리지 않음

### 구조 변경 조건

- 확정값: 책임·의존 방향·배포 단위가 달라질 때 재검토. 모듈 간 원자적 변경·복잡한 규칙·독립 배포 요구 포함. API 추가만으로 구조 문서를 변경하거나 미래 가능성만으로 계층을 추가하지 않음

### 확인 방법

- 확정값: 금지·순환 의존 검사. HTTP·실제 DB 없이 Service 규칙·실패 전달 검증. 실제 DB로 저장 계약·원자성·오류 변환·변경 반영 검증

### 상세 사양

- 확정값: 구체 기능·데이터·API 규칙은 [기능별 동작 규칙](../02-scope.md#기능별-동작-규칙)에서 관리. 새 기능은 기존 모듈 배치 패턴에 적용. 구체 인터페이스·보안·배포·복구 절차는 후속 설계 대상

- 검증 상태: 문서 설계만 작성. 구현·의존 관계 검사·업무 테스트·DB 통합 테스트 미실시.
- 구현 준비 상태: 미완료. 기능·API·DB·보안·운영 상세 사양의 미확정 항목 남음.
