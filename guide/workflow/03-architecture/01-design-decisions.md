# 블로그 서비스의 설계 전제와 기술 선택

## 설계 전제

대상: 회원의 글 작성·관리, 방문자의 공개 글 조회. 예상 규모는 설계 기준.

| 항목 | 설계 전제 |
| --- | --- |
| 예상 시점 | 첫 번째 배포 후 3개월 |
| 전체 사용자 수 | 회원·방문자 합계 1,000명 |
| 동시 사용자 수 | 50명 |
| 주된 이용 | 공개 글 목록·상세 조회 |
| 동작 비중 | 조회 90%, 계정 처리·글 변경 10% |
| 평균 요청량 | 1건/초 = 활성 사용자 10명 × 1건/10초 |
| 집중 시간 요청량 | 10건/초 = 활성 사용자 50명 × 1건/5초 |
| 순간 요청량 | 50건/초 = 활성 사용자 50명 × 1건/초 |
| 글 증가량 | 하루 100개 |
| 글 평균 크기 | 제목·본문 합계 10KiB |
| 데이터 증가량 | 제목·본문 약 1MiB/일. 회원·세션·메타데이터·인덱스 포함 온라인 저장공간 증가 예산 2GiB/년 |
| 클라이언트 | 쿠키 기반 웹 브라우저. 화면 기술 별도 결정 |
| 운영 지역 | 대한민국, 단일 지역 |

요청 빈도·동작 비중·데이터 증가량·운영 지역: 예시 가정. 글 평균 크기: 용량 산정용, 입력 상한 아님.

## 제약조건과 품질 목표

### 실행 환경과 운영 조건

| 항목 | 조건 |
| --- | --- |
| 호스트 운영체제 | Linux |
| 실행 방식 | Docker, 애플리케이션·PostgreSQL 별도 컨테이너 |
| 초기 배치 | 호스트 1대, 애플리케이션·DB 컨테이너 각 1개 |
| 호스트 자원 | 4 vCPU, RAM 8GiB, SSD 100GiB |
| 애플리케이션 상한 | CPU 1개 분량, RAM 1GiB |
| DB 상한 | CPU 2개 분량, RAM 4GiB |
| 자원 여유 | 운영체제·Docker·운영 작업용 |
| 월간 예산 | 10만 원 이내. 서버·저장소·백업·네트워크 포함 |
| 개발·운영 인원 | 1명 |
| 인력 전제 | Go·SQL·Linux·Docker 기본 역량, 정기 운영 주 2시간 |
| 운영 방식 | 자동 상태 확인·장애 알림, 알림 수신 시 대응. 상시 수동 감시 없음 |

고정 조건: Linux·Docker. 예시 가정: 자원·예산·인력. 상품 견적·수용량 실측 아님.
구성요소 추가 시 배포·백업·모니터링 비용 반영.

### 품질 목표

대상: 회원가입·로그인·로그아웃·글 작성·공개 목록·공개 상세·수정·영구 삭제, 총 8개 동작.

| 항목 | 기준 |
| --- | --- |
| 응답시간 | 동시 사용자 100명, 동작별 성공 건 p95 2초 이하 |
| 측정 구간 | 서비스 요청 수신부터 결과 사용 가능 시점까지 |
| 측정 제외 | 클라이언트 네트워크 전송·렌더링·사용자 생각 시간 |
| 월간 가용성 | 동작별 99.5% 이상. 유효하고 권한 있는 요청에 정상 결과 제공 가능한 시간 / 전체 시간 |
| 정상 거부 | 입력·권한 오류의 정상 거부는 비가용에서 제외 |
| 월간 중단 한도 | 전체 시간의 0.5%. 30일 기준 216분, 배포 중단 포함 |
| 복구시간 | 서비스 중단 발생부터 60분 이내 |
| 데이터 복구시점 | DB 전체 복구 시 최대 24시간 전 복구 지점 확보 |
| 변경 반영 | 작성·수정·삭제 성공 응답 후 시작한 조회에 변경 반영 |
| 실패 시 무결성 | 부분 변경 결과의 성공 처리 금지 |

월간 중단 한도: 개별 복구시간 충족 여부와 별도 판정.
단일 호스트의 알림·백업·복구 목표: 복구 훈련으로 검증.

### 보안 조건

- 인증정보·글 변경 요청: HTTPS.
- 비밀번호: 평문 저장·로그 기록 금지.
- 글 수정·삭제: 서버에서 현재 회원·작성자 소유권 확인.
- DB: 클라이언트 직접 접근·공개 서비스 제공 금지.
- DB 자격정보·세션 식별자: 소스 코드·일반 요청 로그 노출 금지.

상세화 대상: 비밀번호 보호·세션·쿠키 보안, 네트워크 접근, 비밀정보 주입.
담당: 보안·시스템·운영 상세 설계.

## 기술과 구조의 선택

### 모듈형 모놀리스

- **필요**: 기능별 책임 분리, 소수 인원의 배포·장애 관리.
- **선택**: 계정·인증, 글 관리, HTTP 처리, 데이터 접근 모듈 분리. 단일 애플리케이션 배포.
- **조건**: 소규모 이용, 1인 운영, 예산 제한.
- **이유**: 내부 호출·단일 DB 트랜잭션, 서비스 간 통신·개별 배포 관리 불필요.
- **대안 제외**: 마이크로서비스는 계약·배포·장애 관리 부담. 모듈 미분리 구조는 변경 경계 불명확.
- **비용**: 배포·프로세스 장애의 전체 영향. 모듈별 독립 배포·개별 확장 불가.

### Go와 표준 HTTP 처리

- **필요**: HTTP API·계정·글 관리 구현.
- **선택**: Go 1.27.3, 표준 `net/http` 서버·라우팅.
- **조건**: 기본 계정·공개 글 기능, 운영자의 Go 역량.
- **이유**: 단일 서버 프로그램, 표준 HTTP 기능 활용, 별도 프레임워크 규약 미도입.
- **대안 제외**: Go 웹 프레임워크는 필수 요구 없음. 타 언어는 현 인력·실행 환경 변경 필요성 없음.
- **비용**: 오류·입력 검증·인증 연결 방식 직접 설계. 외부 라이브러리 사용은 허용.

### PostgreSQL

- **필요**: 회원·세션·글 영속 저장, 고유성·소유 관계·변경 무결성.
- **선택**: PostgreSQL 18.6 단일 기준 저장소. 조회·변경에 같은 DB 사용.
- **조건**: 관계형 데이터, 변경 성공 후 최신 결과 조회.
- **이유**: 고유성·참조 제약, 연관 변경의 트랜잭션 처리.
- **대안 제외**: SQLite 대신 독립 컨테이너형 PostgreSQL 채택. 문서형 저장소는 필수 요구 없음. 다중 저장소는 일관성·복구 경계 증가.
- **비용**: DB 프로세스·연결·마이그레이션·백업 운영. 단일 DB 장애의 전체 영향.

### Linux와 Docker의 단일 호스트 배치

- **필요**: 실행 환경 분리, 동일 구성 배포.
- **선택**: Linux 호스트 1대, 애플리케이션·DB 별도 Docker 컨테이너. DB 데이터는 컨테이너 교체와 분리 보존.
- **조건**: Linux·Docker 고정, 자원 상한·1인 운영·예산 제한.
- **이유**: 단일 호스트 유지, 실행·교체 단위 분리.
- **대안 제외**: 직접 설치는 컨테이너 배포 조건 불충족. 다중 호스트 오케스트레이션·DB 이중화는 첫 배포에서 미채택.
- **비용**: 호스트 장애·자원 경쟁의 동시 영향. 고가용성 미보장.

시스템·배포 상세화: Linux 배포판, Docker 버전, 이미지 고정, 네트워크·볼륨 설정.

### 데이터베이스에 저장하는 서버 세션

- **필요**: 요청별 회원 식별, 로그아웃 후 해당 이용 상태의 회원 전용 동작 차단.
- **선택**: 쿠키로 세션 식별자 전달, PostgreSQL 세션 확인. 계정 정보·수명·유효성은 서버 관리.
- **조건**: 브라우저 이용, 현재 이용 상태의 로그아웃, 단일 저장소.
- **이유**: 서버에서 로그인 유효성·폐기 관리, 별도 세션 저장소 불필요.
- **대안 제외**: 자체 완결형 토큰은 로그아웃·폐기 규칙 추가 필요. Redis 세션은 저장소 운영 부담 증가.
- **비용**: 세션 조회·만료 정리, 쿠키 보안·요청 위조 방어.

### 별도 캐시·메시지 브로커·검색 서버 미도입

- **필요**: 구현·운영 구성 최소화.
- **선택**: 계정·글 처리는 애플리케이션·PostgreSQL로 한정.
- **조건**: 검색·미디어 업로드 제외, 공개 글 변경 즉시 반영.
- **이유**: 비동기 공개 갱신·캐시 무효화 경계 없이 단일 저장소 사용.
- **대안 유예**: 캐시 조회 분산·브로커 작업 분리·검색 서버는 필요 확인 후 재검토.
- **비용**: 조회·변경 부하 집중. 목표 미달 시 쿼리·인덱스·연결·자원 배치부터 확인.

## 검증 및 재검토 기준

### 검증 환경과 부하

| 항목 | 조건 |
| --- | --- |
| 서버 | 별도 Linux 호스트, 운영과 동일 자원·이미지·컨테이너 상한 |
| 부하 발생기 | 서버와 별도 호스트 |
| 시작 데이터 | 합성 계정 1,000개, 공개 글 100,000개, 제목·본문 평균 합계 10KiB |
| 데이터 규모 근거 | 예상 3개월 약 9,000개보다 큰 누적 데이터 조건 |
| 지속 부하 | 가상 사용자 100명 × 평균 1건/5초 = 20건/초 |
| 로그인 필요 동작 | 유효 계정·세션 사용, 수정·삭제는 본인 소유 글 |
| 회원가입 | 미등록 이메일 사용 |
| 데이터 변화 | 글 생성·삭제 내역을 측정 결과와 함께 기록 |
| 성공 표본 | 동작별 최소 1,000건 |
| p95 계산 | 동작별 성공 완료 시간 오름차순, `ceil(0.95 × 표본 수)`번째 값 |
| 예기치 않은 실패 | 유효하고 권한 있는 요청의 실패를 기능·안정성 문제로 별도 기록 |
| 집중 요청 | 로그인 사용자 100명, 동일 시작 신호, 각자 유효 요청 1건 동시 전송 |
| 집중 요청 판정 | 오류·자원 포화 별도 확인. 지속 부하 p95와 합산 금지 |

혼합 부하: 공개 목록 45%, 공개 상세 45%, 로그인 3%, 로그아웃 2%, 글 작성 2%, 수정 2%, 회원가입 0.5%, 영구 삭제 0.5%.

검증 대상 8개 동작과 API 개수·경로는 별개. 실제 요청 구성은 API 설계 후 확정.
