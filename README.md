# 했다쳐 (Haetdachyeo)

> 구현했다고 쳐.

했다쳐는 애플리케이션을 구현하는 프로젝트가 아닙니다.

여러 프로젝트의 요구사항과 설계를 **구현 결과가 결정되는 수준까지 완성**하고, 이를 각각의 GitHub Repository로 관리하는 GitHub Organization입니다.

프로젝트 문서만 AI 또는 개발자에게 제공해도 추가적인 핵심 설계나 질문 없이 구현을 시작할 수 있어야 합니다. 누가 구현하더라도 기능, 외부 계약, 도메인 규칙, 데이터 모델, 아키텍처와 운영 특성이 사전에 정의된 범위 안에서 실질적으로 동일한 결과로 수렴하는 상태를 목표로 합니다.

그 상태에 도달하면 실제 구현은 새로운 판단이 아니라 이미 결정된 설계를 코드로 옮기는 반복 작업이 됩니다. 했다쳐는 구현할 수 없어서 구현하지 않는 것이 아니라, **설계로 구현 결과를 충분히 결정했기 때문에 구현을 생략합니다.**

## 왜 만드는가

AI의 발전으로 요구사항과 적절한 컨텍스트가 주어졌을 때 애플리케이션을 구현하는 일은 이전보다 쉬워졌습니다. 그러나 프로젝트의 품질을 결정하는 다음 판단은 여전히 개발자의 책임입니다.

- 무엇을 만들고 무엇을 만들지 않을 것인가
- 도메인과 시스템의 경계를 어떻게 나눌 것인가
- 데이터를 어떻게 모델링할 것인가
- 외부 인터페이스와 상태 전이를 어떻게 정의할 것인가
- 어떤 아키텍처, 인프라와 기술을 선택할 것인가
- 현재 요구사항에 어느 수준의 확장성이 필요한가
- 선택 가능한 대안과 각각의 트레이드오프는 무엇인가

했다쳐는 코드를 작성하기 전에 필요한 이러한 판단에 집중합니다. 문서를 많이 만드는 것이 아니라, **구현에 필요한 의사결정을 문서로 확정하는 것**이 목적입니다.

## 이름의 의미

**했다쳐**는 **“구현했다고 쳐”**라는 뜻입니다.

요구사항과 설계가 충분히 구체적이어서 AI가 핵심 사항을 스스로 판단하지 않아도 되고, 서로 다른 구현 주체가 실질적으로 동등한 결과물을 만들 수 있다면 다음과 같이 봅니다.

> 이 정도면 구현은 했다 쳐.

## 목표

각 프로젝트의 최종 상태는 다음과 같습니다.

> 프로젝트 문서만 AI 또는 개발자에게 제공해도 추가적인 질문이나 핵심 설계 없이 구현할 수 있는 상태

여기서 동일한 결과란 소스 코드가 문자 단위로 같다는 뜻이 아닙니다. 다음과 같이 제품과 시스템의 동작을 결정하는 요소가 동일하다는 뜻입니다.

- 제공하는 기능과 비범위
- 사용자에게 보이는 동작과 결과
- 정상, 예외, 실패와 경계 조건
- 도메인 규칙과 상태 전이
- API와 외부 시스템 계약
- 데이터 구조와 영속성 규칙
- 시스템 구성과 기술 선택
- 보안, 성능, 가용성과 운영 기준
- 테스트 및 인수 조건

변수명이나 코드 배치처럼 결과를 바꾸지 않는 세부 구현은 달라질 수 있습니다. 그러나 결과에 영향을 주는 판단은 AI의 재량으로 남겨두지 않습니다.

## 기본 원칙

- **애플리케이션 코드를 구현하지 않는다.**
- **요구사항을 설계와 기술보다 먼저 확정한다.**
- **범위뿐 아니라 비범위도 명시한다.**
- **정상 흐름과 함께 예외, 실패, 경계 조건을 정의한다.**
- **AI가 추측해야 하는 핵심 설계 판단을 남기지 않는다.**
- **단순함을 우선하고 오버엔지니어링하지 않는다.**
- **확인된 요구사항과 합리적으로 예상 가능한 변화에 필요한 확장성은 확보한다.**
- **중요한 선택에는 이유, 대안과 트레이드오프를 기록한다.**
- **문서의 양이 아니라 구현 가능성을 기준으로 완성도를 판단한다.**

## 프로젝트에서 설계하는 것

프로젝트의 특성과 규모에 따라 다음 영역을 필요한 수준까지 설계합니다.

```text
README
Requirements
Use Cases
Domain
Architecture
API
Database
Infrastructure
Security
Operations
ADR
AI Instructions
```

모든 영역을 형식적으로 채우거나 하나의 Markdown 파일에 강제하지 않습니다. 내용이 커지면 도메인 또는 관심사에 따라 문서를 분리합니다.

예를 들어 API 문서는 다음과 같이 구성할 수 있습니다.

```text
api/
├── README.md
├── common.md
├── auth.md
├── users.md
└── projects.md
```

문서 구조와 깊이는 프로젝트 규모, 복잡도와 구현에 필요한 정보량을 기준으로 결정합니다.

## 설계 결정 기록

중요한 결정은 최종 선택만 기록하지 않습니다. 가능한 한 다음 내용을 함께 남깁니다.

1. **문제**: 해결해야 하는 문제가 무엇인가
2. **제약사항**: 선택을 제한하는 조건은 무엇인가
3. **선택**: 무엇을 선택했는가
4. **이유**: 왜 이 선택이 현재 요구사항에 적합한가
5. **대안**: 어떤 선택지를 검토했는가
6. **트레이드오프**: 무엇을 얻고 무엇을 포기했는가

“PostgreSQL을 사용한다”는 결론만으로는 부족합니다. 현재 요구사항과 제약에서 PostgreSQL을 선택한 이유, 다른 대안을 선택하지 않은 이유와 그 결정의 비용까지 설명해야 합니다.

## 설계 수준

했다쳐는 모든 미래를 미리 설계하는 프로젝트가 아닙니다.

현재 요구사항을 구현하는 데 필요한 결정을 완료하되, 이후의 합리적인 변경이 지나치게 어려워지는 구조는 피합니다. 확장성은 막연한 가능성이 아니라 다음 근거를 바탕으로 판단합니다.

- 현재 확정된 요구사항
- 예상되는 사용량과 품질 기준
- 이미 확인된 후속 요구사항
- 변경 가능성이 높고 변경 비용이 큰 지점

근거 없는 추상화와 범용화는 추가하지 않습니다.

## AI의 역할

AI는 프로젝트의 주요 설계 결정을 대신하는 주체가 아닙니다.

설계 단계에서는 다음을 지원하는 검토 도구로 활용할 수 있습니다.

- 누락된 요구사항과 모호한 표현 탐색
- 설계 대안 조사
- 장단점과 트레이드오프 분석
- 문서 간 모순과 누락 검증
- 문서 구조화와 표현 개선

구현 단계에서 AI는 개발자가 확정한 설계를 코드로 변환하는 실행자입니다. 문서에 없는 핵심 사항을 관습이나 추측으로 결정해서는 안 됩니다. AI가 추가 질문을 해야 하거나 결과를 바꿀 수 있는 판단을 직접 내려야 한다면, 구현 능력의 문제가 아니라 설계가 아직 완료되지 않은 것입니다.

## GitHub 구성

GitHub Organization `haetdachyeo` 아래에서 각 설계 프로젝트를 독립적인 Repository로 관리합니다.

```text
haetdachyeo/
├── haetdachyeo
├── project-a
├── project-b
├── project-c
└── ...
```

각 Repository는 하나의 독립된 설계 프로젝트입니다.

### `haetdachyeo/haetdachyeo`

이 Repository는 개별 프로젝트가 아니라 Organization 전체의 기준을 관리하는 메인 Repository입니다.

- 했다쳐의 목적과 철학
- 프로젝트 원칙
- 필수 설계 항목
- 문서 작성 기준
- 프로젝트 완료 기준
- 프로젝트 Template
- AI 활용 기준

## 완료 기준

프로젝트의 핵심 완료 기준은 하나입니다.

> 추가적인 질문이나 핵심 설계 없이 구현을 시작할 수 있는가?

AI 또는 개발자가 다음 질문을 다시 해야 한다면 설계가 부족한 것으로 봅니다.

- 무엇을 만들어야 하는가?
- 무엇을 만들지 않아야 하는가?
- 사용자와 시스템은 각 상황에서 어떻게 동작해야 하는가?
- 오류와 경계 조건은 어떻게 처리해야 하는가?
- 시스템은 어떤 구성과 책임으로 나뉘는가?
- 데이터는 어떤 규칙으로 저장되고 변경되는가?
- 외부 인터페이스는 무엇이며 어떤 계약을 따르는가?
- 어디에 어떻게 배포하고 운영하는가?
- 어떤 기술을 사용하며 왜 선택했는가?
- 구현 결과가 요구사항과 일치하는지 어떻게 검증하는가?

이 질문들에 프로젝트 문서가 일관되고 검증 가능한 답을 제공하며, 구현 주체의 핵심 설계 재량이 남지 않은 상태를 **했다쳐의 완료 상태**로 정의합니다.
