# 했다쳐 (Haetdachyeo)

[한국어](README.md) | [English](README.en.md) | [日本語](README.ja.md)

> 구현했다고 쳐.

했다쳐는 **구현 결과가 결정되는 수준까지 요구사항과 설계를 완성**하는 GitHub Organization입니다. 각 설계 프로젝트는 독립 Repository로 관리합니다.

목표는 AI나 개발자가 문서만으로 추가 질문이나 핵심 설계 없이 구현하는 것. 구현 주체가 달라도 기능·계약·도메인·데이터·아키텍처·운영 특성이 동등해야 합니다.

직접 애플리케이션을 구현하지 않습니다. **설계로 결과를 결정하고, 구현은 확정된 설계의 코드 변환으로 남깁니다.**

## 왜 만드는가

AI 구현은 쉬워져도 제품과 시스템의 판단은 개발자의 책임입니다.

- 포함·제외 범위
- 도메인·시스템 경계
- 데이터 모델·상태 전이·외부 계약
- 아키텍처·인프라·기술·확장성
- 대안과 트레이드오프

목적은 문서의 양이 아니라 **구현에 필요한 의사결정의 확정**입니다.

## 이름의 의미

**했다쳐 = “구현했다고 쳐.”**

핵심 판단 없이도 서로 동등한 구현이 가능한 설계라면, “이 정도면 구현은 했다 쳐”라고 봅니다.

## 목표

> 프로젝트 문서만 AI 또는 개발자에게 제공해도 추가적인 질문이나 핵심 설계 없이 구현할 수 있는 상태

동등해야 할 대상:

- 기능·비범위, 사용자 동작·결과
- 정상·예외·실패·경계 조건
- 도메인 규칙·상태 전이
- API·외부 시스템 계약
- 데이터 구조·영속성
- 시스템 구성·기술 선택
- 보안·성능·가용성·운영
- 테스트·인수 조건

소스 코드의 문자 단위 일치는 목표가 아닙니다. 변수명·코드 배치 등 결과에 영향 없는 차이는 허용하되, 결과를 바꾸는 판단은 AI 재량으로 남기지 않습니다.

## 기본 원칙

- 애플리케이션 코드 구현 제외.
- 요구사항 확정 후 설계·기술 선택.
- 포함·제외 범위 명시.
- 정상·예외·실패·경계 조건 정의.
- AI의 핵심 설계 추측 금지.
- 단순함 우선, 과잉 설계 금지.
- 확정 요구사항·합리적 예상 변화에 필요한 확장성 확보.
- 선택 이유·대안·트레이드오프 기록.
- 문서량보다 구현 가능성으로 완성도 판단.

## 프로젝트에서 설계하는 것

[설계 워크플로우](guide/workflow/): 작성 양식과 블로그 서비스 예시.

1. [목적](guide/workflow/01-purpose.md): 목적·배경·사용자·규모·가치·성공 기준
2. [스코프](guide/workflow/02-scope.md): 포함·제외 범위, 기능 경계
3. [기술과 아키텍처](guide/workflow/03-architecture.md): 설계 방향·구성·기술, 상세 설계 안내

- `*.example.md`: 작성자가 고민하고 채울 양식.
- 같은 단계의 일반 문서: 블로그 서비스 작성 예시.
- 아키텍처 대표 문서: 전체 요약. 상세 설계: `03-architecture/`.

프로젝트 특성·규모에 따라 필요한 영역을 설계합니다.

```text
README
Requirements
Use Cases
Domain
Architecture
API
Database
Infrastructure
Security
Operations
ADR
AI Instructions
```

형식적인 전 영역 작성이나 단일 Markdown 파일을 강제하지 않습니다. 규모·복잡도·필요 정보량에 따라 도메인·관심사별로 분리합니다.

API 문서 분리 예:

```text
api/
├── README.md
├── common.md
├── auth.md
├── users.md
└── projects.md
```

## 설계 결정 기록

중요 결정의 기록 항목:

| 항목 | 내용 |
| --- | --- |
| 문제 | 해결 대상 |
| 제약사항 | 선택을 제한하는 조건 |
| 선택 | 채택한 방식 |
| 이유 | 현재 요구사항에 적합한 근거 |
| 대안 | 검토한 선택지와 제외 이유 |

예: PostgreSQL 채택 여부뿐 아니라 적합성·대안 제외 이유·비용까지 기록.

## 설계 수준

현재 구현에 필요한 결정을 완료하되, 합리적인 후속 변경을 막는 구조는 피합니다.

확장성의 판단 근거:

- 확정 요구사항
- 예상 사용량·품질 기준
- 확인된 후속 요구사항
- 변경 가능성·비용이 큰 지점

모든 미래의 선제 설계, 근거 없는 추상화·범용화는 제외합니다.

## AI의 역할

| 단계 | 역할 |
| --- | --- |
| 설계 | 누락·모호함 탐색, 대안 조사, 장단점·트레이드오프 분석, 문서 모순 검증·구조화·표현 개선 |
| 구현 | 개발자가 확정한 설계를 코드로 변환 |

주요 설계 판단을 대신하거나 문서 밖 핵심 사항을 추측하지 않습니다. 추가 질문이나 결과를 바꾸는 판단이 필요하다면 설계 미완료입니다.

## 사양서와 구현의 동기화

**현재 사양서만으로 프로젝트의 전체 사양을 파악할 수 있어야 합니다.** 프로젝트 유지 기간 내내 의도한 동작의 최신 기준으로 관리합니다.

- 변경: 별도 수정 사양서 대신 **기존 사양서 직접 수정**.
- API 변경: 입력·출력·오류·관련 규칙을 변경 후 전체 사양으로 갱신.
- 영향 범위: 관련 사양도 함께 갱신, 문서 일관성 유지.
- 이력: Git 관리. 과거 변경 문서·이력 조합 없이 현재 동작 파악.

AI 동기화 순서:

1. 사양 변경점과 현재 구현의 차이 파악.
2. 영향받는 코드·테스트를 최신 사양에 맞춰 수정.
3. 실제 동작·관련 테스트로 사양 일치 검증.

누락·모순은 구현 전 사양에서 해결합니다. **코드에 사양을 맞추지 않고, 확정된 사양에 코드·테스트를 맞춥니다.**

## 장기 목표

설계 사례가 충분히 축적된 뒤 **AI 개발의 표준**을 만드는 것이 장기 목표입니다. 현재의 즉각적인 범위는 아닙니다. 검토·확정한 설계 방식을 프로젝트 조건에 맞게 재사용합니다.

| 자산 | 내용 |
| --- | --- |
| 설계 틀 | API·인증·실시간 통신·저장·배포·운영 등 재사용 단위 |
| 결정 규칙 | 조건별 틀의 선택·제외 기준 |
| 조합 규칙 | 틀 사이의 의존성·호환성·충돌·통합 기준 |

핵심 자산은 **결정 규칙**입니다. 기능·트래픽·예산·보안·클라이언트·운영 역량·품질을 함께 판단합니다. “블로그=REST”, “모바일=JWT”처럼 고정하지 않으며, 각 틀에 적용·제외 조건과 대안·트레이드오프를 기록합니다.

```text
서비스 기능과 제약조건
        ↓
적용 가능한 설계 틀과 결정 규칙 탐색
        ↓
호환성, 비용과 트레이드오프 분석
        ↓
프로젝트에 맞게 조립된 설계 초안
        ↓
개발자 또는 사용자의 검토와 확정
        ↓
확정된 프로젝트 명세에 따른 AI 구현
```

AI 초안은 상용 적합성을 보장하지 않습니다. 구현 전 개발자·사용자가 현재 요구사항·제약에 맞는지 검토·확정합니다.

## 완료 기준

> 추가적인 질문이나 핵심 설계 없이 구현을 시작할 수 있는가?

문서가 답해야 할 항목:

- 포함·제외 범위
- 사용자·시스템의 상황별 동작
- 오류·경계 조건 처리
- 시스템 구성·책임
- 데이터 저장·변경 규칙
- 외부 인터페이스·계약
- 배포·운영 방식
- 기술 선택·이유
- 요구사항 일치 검증 방법

일관되고 검증 가능한 답이 있고, 구현 주체의 핵심 설계 재량이 남지 않은 상태가 **완료**입니다.
