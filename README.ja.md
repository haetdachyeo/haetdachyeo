# 했다쳐 (Haetdachyeo)

[한국어](README.md) | [English](README.en.md) | [日本語](README.ja.md)

> 実装したことにしよう。

Haetdachyeoは、**実装結果が決まる水準まで要件と設計を完成**させるGitHub Organizationです。設計プロジェクトごとに独立したRepositoryで管理します。

目標は、AIや開発者が文書だけで、追加の質問や重要な設計判断なしに実装できること。実装者が異なっても、機能・契約・ドメイン・データ・アーキテクチャ・運用特性が同等になる状態を目指します。

アプリケーション自体は実装しません。**設計で結果を決め、実装は確定済み設計のコードへの変換とします。**

## なぜ作るのか

AIによる実装が容易になっても、製品とシステムの判断は開発者の責任です。

- 対象・対象外の範囲
- ドメイン・システムの境界
- データモデル・状態遷移・外部契約
- アーキテクチャ・インフラ・技術・拡張性
- 代替案とトレードオフ

目的は文書量ではなく、**実装に必要な意思決定の確定**です。

## 名前の意味

**Haetdachyeo（했다쳐）＝「実装したことにしよう」。**

重要な判断なしに同等の実装ができる設計なら、「この程度なら実装したことにしよう」と考えます。

## 目標

> プロジェクト文書だけで、AIや開発者が追加の質問や重要な設計判断なしに実装できる状態

同等であるべき対象：

- 機能・対象外範囲、ユーザーの動作・結果
- 正常・例外・失敗・境界条件
- ドメインルール・状態遷移
- API・外部システムとの契約
- データ構造・永続性
- システム構成・技術選択
- セキュリティ・性能・可用性・運用
- テスト・受け入れ条件

ソースコードの文字単位の一致は目標ではありません。変数名・コード配置など結果に影響しない違いは許容し、結果を変える判断はAIの裁量に残しません。

## 基本原則

- アプリケーションコードの実装は対象外。
- 要件確定後に設計・技術選択。
- 対象・対象外の範囲を明示。
- 正常・例外・失敗・境界条件を定義。
- AIによる重要な設計判断の推測を禁止。
- 単純さ優先、過剰設計を回避。
- 確定要件・合理的な想定変更に必要な拡張性を確保。
- 選択理由・代替案・トレードオフを記録。
- 文書量より実装可能性で完成度を判断。

## プロジェクトで設計するもの

[設計ワークフロー](guide/workflow/)：記入用テンプレートとブログサービスの例。

1. [目的](guide/workflow/01-purpose.ja.md)：目的・背景・ユーザー・規模・価値・成功基準
2. [範囲](guide/workflow/02-scope.ja.md)：対象・対象外の範囲、機能の境界
3. [技術とアーキテクチャ](guide/workflow/03-architecture.ja.md)：設計方針・構成・技術、詳細設計の案内

- `*.example.md`：作成者が検討・記入するテンプレート。
- 同じ段階の通常文書：ブログサービスの記入例。
- アーキテクチャ代表文書：全体の要約。詳細設計：`03-architecture/`。

プロジェクトの特性・規模に応じて必要な領域を設計します。

```text
README
Requirements
Use Cases
Domain
Architecture
API
Database
Infrastructure
Security
Operations
ADR
AI Instructions
```

形式的な全領域の記入や単一Markdownファイルは強制しません。規模・複雑さ・必要情報量に応じ、ドメイン・関心事別に分割します。

API文書の分割例：

```text
api/
├── README.md
├── common.md
├── auth.md
├── users.md
└── projects.md
```

## 設計上の意思決定の記録

重要な決定の記録項目：

| 項目 | 内容 |
| --- | --- |
| 問題 | 解決すべき対象 |
| 制約条件 | 選択を制限する条件 |
| 選択 | 採用した方式 |
| 理由 | 現在の要件に適する根拠 |
| 代替案 | 検討した選択肢と除外理由 |
| トレードオフ | 得るもの・諦めるもの・コスト |

例：PostgreSQLの採用だけでなく、適合性・代替案の除外理由・コストまで記録。

## 設計の水準

現在の実装に必要な判断を完了しつつ、合理的な後続変更を妨げる構造は避けます。

拡張性の判断根拠：

- 確定要件
- 想定利用量・品質基準
- 確認済みの後続要件
- 変更の可能性・コストが大きい箇所

すべての将来を先取りする設計、根拠のない抽象化・汎用化は対象外です。

## AIの役割

| 段階 | 役割 |
| --- | --- |
| 設計 | 欠落・曖昧さの検出、代替案調査、長所・短所・トレードオフ分析、文書の矛盾検証・構造化・表現改善 |
| 実装 | 開発者が確定した設計をコードに変換 |

主要な設計判断の代行や、文書にない重要事項の推測はしません。追加の質問や結果を変える判断が必要なら、設計は未完了です。

## 仕様書と実装の同期

**現在の仕様書だけでプロジェクトの全仕様を把握できること。** 維持期間を通じ、意図した動作の最新基準として管理します。

- 変更：別の変更仕様書ではなく、**既存の仕様書を直接更新**。
- API変更：入力・出力・エラー・関連ルールを変更後の全仕様に更新。
- 影響範囲：関連仕様も更新し、文書間の一貫性を維持。
- 履歴：Git管理。過去の変更文書・履歴の組み合わせなしに現在の動作を把握。

AIによる同期手順：

1. 仕様の変更点と現在の実装との差を把握。
2. 影響するコード・テストを最新仕様に合わせて修正。
3. 実際の動作・関連テストで仕様との一致を検証。

欠落・矛盾は実装前に仕様で解決します。**コードに仕様を合わせず、確定仕様にコード・テストを合わせます。**

## 長期目標

設計事例が十分に蓄積した後、**AI開発の標準**を作ることが長期目標です。現在の直近の範囲ではありません。検討・確定した設計方式をプロジェクト条件に合わせて再利用します。

| 資産 | 内容 |
| --- | --- |
| 設計テンプレート | API・認証・リアルタイム通信・保存・デプロイ・運用などの再利用単位 |
| 意思決定ルール | 条件別のテンプレート選択・除外基準 |
| 組み合わせルール | テンプレート間の依存・互換性・競合・統合基準 |

中核は**意思決定ルール**です。機能・トラフィック・予算・セキュリティ・クライアント・運用能力・品質を総合判断します。「ブログ＝REST」「モバイル＝JWT」と固定せず、各テンプレートに適用・除外条件、代替案・トレードオフを記録します。

```text
サービスの機能と制約条件
        ↓
適用可能な設計テンプレートと意思決定ルールを探索
        ↓
互換性・コスト・トレードオフを分析
        ↓
プロジェクトに合う設計案を組み立てる
        ↓
開発者またはユーザーによるレビューと確定
        ↓
確定したプロジェクト仕様に基づくAI実装
```

AIの案は商用適合性を保証しません。実装前に開発者・ユーザーが現在の要件・制約との適合をレビューし、確定します。

## GitHubの構成

GitHub Organization `haetdachyeo`配下に、設計プロジェクト別の独立Repositoryを置きます。

```text
haetdachyeo/
├── haetdachyeo
├── project-a
├── project-b
├── project-c
└── ...
```

### `haetdachyeo/haetdachyeo`

個別の設計プロジェクトではなく、Organizationの基準を管理するメインRepository。

- 目的・思想・プロジェクト原則
- 必須設計項目・記入基準・完了基準
- プロジェクトテンプレート・AI活用基準

## 完了基準

> 追加の質問や重要な設計判断なしに実装を開始できるか。

文書が答えるべき項目：

- 対象・対象外の範囲
- ユーザー・システムの状況別動作
- エラー・境界条件の処理
- システム構成・責務
- データの保存・変更ルール
- 外部インターフェース・契約
- デプロイ・運用方式
- 技術選択・理由
- 要件との一致を検証する方法

一貫した検証可能な答えがあり、実装者に重要な設計判断の裁量が残らない状態を**完了**とします。
