# 했다쳐 (Haetdachyeo)

[한국어](README.md) | [English](README.en.md) | [日本語](README.ja.md)

> 実装したことにしよう。

Haetdachyeoは、アプリケーションを実装するプロジェクトではありません。

複数のプロジェクトの要件と設計を、**実装結果が決定される水準まで完成**させ、それぞれをGitHub Repositoryとして管理するGitHub Organizationです。

プロジェクト文書だけをAIまたは開発者に提供しても、追加の重要な設計判断や質問を必要とせず、実装を開始できなければなりません。誰が実装しても、機能、外部契約、ドメインルール、データモデル、アーキテクチャ、および運用特性が、あらかじめ定義された範囲内で実質的に同等の結果へ収束する状態を目指します。

この状態に達すれば、実際の実装は新たな判断ではなく、すでに確定した設計をコードに移す反復作業となります。Haetdachyeoが実装を省略するのは、実装できないからではなく、**設計によって実装結果を十分に決定しているからです。**

## なぜ作るのか

AIの発展により、要件と適切なコンテキストが与えられた際にアプリケーションを実装することは、以前より容易になりました。しかし、プロジェクトの品質を決定する以下の判断は、今なお開発者の責任です。

- 何を作り、何を作らないのか
- ドメインとシステムの境界をどのように分けるのか
- データをどのようにモデル化するのか
- 外部インターフェースと状態遷移をどのように定義するのか
- どのアーキテクチャ、インフラストラクチャ、および技術を選択するのか
- 現在の要件にどの程度の拡張性が必要なのか
- 選択可能な代替案と、それぞれのトレードオフは何か

Haetdachyeoは、コードを書く前に必要となるこれらの判断に集中します。文書を大量に作成することではなく、**実装に必要な意思決定を文書として確定すること**が目的です。

## 名前の意味

**Haetdachyeo（했다쳐）**は、韓国語の**「구현했다고 쳐」**、すなわち**「実装したことにしよう」**という意味です。

要件と設計が十分に具体的であり、AIが重要事項を自ら判断する必要がなく、異なる実装者が実質的に同等の成果物を作成できるなら、次のように考えます。

> この程度なら、実装したことにしよう。

## 目標

各プロジェクトが目指す最終状態は、次のとおりです。

> プロジェクト文書だけをAIまたは開発者に提供しても、追加の質問や重要な設計判断なしに実装できる状態

ここでいう同等の結果とは、ソースコードが文字単位で同一であることを意味しません。次のような、プロダクトとシステムの振る舞いを決定する要素が同等であることを意味します。

- 提供する機能と対象外範囲
- ユーザーから見える振る舞いと結果
- 正常、例外、失敗、および境界条件
- ドメインルールと状態遷移
- APIと外部システムとの契約
- データ構造と永続化ルール
- システム構成と技術選択
- セキュリティ、性能、可用性、および運用基準
- テストおよび受け入れ条件

変数名やコードの配置など、結果を変えない実装上の詳細は異なる場合があります。しかし、結果に影響する判断をAIの裁量には委ねません。

## 基本原則

- **アプリケーションコードを実装しない。**
- **設計や技術より先に要件を確定する。**
- **対象範囲だけでなく、対象外範囲も明示する。**
- **正常フローとともに、例外、失敗、および境界条件を定義する。**
- **AIが推測しなければならない重要な設計判断を残さない。**
- **単純さを優先し、過剰設計を避ける。**
- **確定した要件と合理的に予測できる変更に必要な拡張性を確保する。**
- **重要な選択について、理由、代替案、およびトレードオフを記録する。**
- **文書の量ではなく、実装可能性を基準に完成度を判断する。**

## プロジェクトで設計するもの

プロジェクトの特性と規模に応じて、次の領域を必要な水準まで設計します。

```text
README
Requirements
Use Cases
Domain
Architecture
API
Database
Infrastructure
Security
Operations
ADR
AI Instructions
```

すべての領域を形式的に埋めることや、1つのMarkdownファイルにまとめることを強制しません。内容が増えた場合は、ドメインまたは関心事ごとに文書を分割します。

たとえば、API文書は次のように構成できます。

```text
api/
├── README.md
├── common.md
├── auth.md
├── users.md
└── projects.md
```

文書の構造と詳細度は、プロジェクトの規模、複雑さ、および実装に必要な情報量を基準に決定します。

## 設計上の意思決定の記録

重要な意思決定では、最終的な選択だけを記録するのではありません。可能な限り、次の内容も併せて残します。

1. **問題**：解決すべき問題は何か
2. **制約条件**：選択を制限する条件は何か
3. **選択**：何を選択したのか
4. **理由**：なぜこの選択が現在の要件に適しているのか
5. **代替案**：どのような選択肢を検討したのか
6. **トレードオフ**：何を得て、何を断念したのか

「PostgreSQLを使用する」という結論だけでは不十分です。現在の要件と制約のもとでPostgreSQLを選択した理由、他の代替案を選択しなかった理由、そしてその意思決定に伴うコストまで説明しなければなりません。

## 設計の水準

Haetdachyeoは、あらゆる将来を事前に設計するプロジェクトではありません。

現在の要件を実装するために必要な意思決定を完了させる一方で、将来の合理的な変更が過度に困難になる構造は避けます。拡張性は漠然とした可能性ではなく、次の根拠に基づいて判断します。

- 現時点で確定している要件
- 想定される利用量と品質基準
- すでに確認されている後続要件
- 変更される可能性が高く、変更コストも大きい箇所

根拠のない抽象化や汎用化は追加しません。

## AIの役割

AIは、プロジェクトの主要な設計判断を開発者に代わって行う主体ではありません。

設計段階では、次の作業を支援するレビュー手段として活用できます。

- 欠落している要件や曖昧な表現の検出
- 設計上の代替案の調査
- 長所、短所、およびトレードオフの分析
- 文書間の矛盾や欠落の検証
- 文書の構造化と表現の改善

実装段階において、AIは開発者が確定した設計をコードへ変換する実行者です。文書に記載されていない重要事項を、慣習や推測によって決定してはなりません。AIが追加の質問をする必要がある場合、または結果を変え得る判断を自ら下さなければならない場合、それは実装能力の問題ではなく、設計がまだ完了していないことを意味します。

## 長期目標

以下は現在のプロジェクトの直近の対象範囲ではなく、設計プロジェクトが十分に蓄積された時点で目指す長期的な方向性です。

Haetdachyeoの最終目標は、蓄積されたプロジェクトの設計判断から繰り返し利用できる基準を抽出し、**AI開発の標準を作ること**です。新しいプロジェクトを毎回ゼロから設計するのではなく、過去のプロジェクトで検討し確定した方式を、現在の条件に合わせて組み立てられるようにします。

そのために、次の3種類の資産を蓄積します。

1. **設計テンプレート**：API、認証、リアルタイム通信、データ保存、デプロイ、運用など、再利用可能な設計単位
2. **意思決定ルール**：どの条件でどのテンプレートを選択または除外すべきかを定義する基準
3. **組み合わせルール**：選択したテンプレート間の依存関係、互換性、競合、および統合方法を定義する基準

これらの中で最も重要な資産は、**意思決定ルール**です。必要な機能だけでなく、トラフィック、予算、セキュリティ水準、クライアント、運用能力、および品質要件を併せて分析して初めて、プロジェクトに適した設計を選択できるからです。

したがって、「ブログにはREST」「モバイルアプリにはJWT」のように、1つの機能を1つの技術に固定しません。同じ機能でも、プロジェクトの条件と制約によって異なる選択が適切な場合があります。各テンプレートには、適用条件、除外条件、代替案、およびトレードオフを併せて定義する必要があります。

長期的には、次の流れを目指します。

```text
サービスの機能と制約条件
        ↓
適用可能な設計テンプレートと意思決定ルールを探索
        ↓
互換性、コスト、トレードオフを分析
        ↓
プロジェクトに合わせた設計案を組み立てる
        ↓
開発者またはユーザーによるレビューと確定
        ↓
確定したプロジェクト仕様に基づくAI実装
```

AIは蓄積された標準を根拠として設計案を提示できますが、その案が自動的に商用サービスへ適用可能であるとはみなしません。実装前に、開発者またはユーザーが現在のプロジェクトの要件と制約に適合しているかをレビューし、確定する必要があります。

## GitHubの構成

GitHub Organization `haetdachyeo`の配下で、各設計プロジェクトを独立したRepositoryとして管理します。

```text
haetdachyeo/
├── haetdachyeo
├── project-a
├── project-b
├── project-c
└── ...
```

各Repositoryは、それぞれ独立した1つの設計プロジェクトです。

### `haetdachyeo/haetdachyeo`

このRepositoryは個別のプロジェクトではなく、Organization全体の基準を管理するメインRepositoryです。

- Haetdachyeoの目的と思想
- プロジェクトの原則
- 必須の設計項目
- 文書作成基準
- プロジェクトの完了基準
- プロジェクトTemplate
- AI活用基準

## 完了基準

プロジェクトの中核となる完了基準は、1つです。

> 追加の質問や重要な設計判断なしに、実装を開始できるか。

AIまたは開発者が次の質問を改めてしなければならない場合、設計が不十分であると判断します。

- 何を作るべきか。
- 何を作るべきではないか。
- ユーザーとシステムは、それぞれの状況でどのように振る舞うべきか。
- エラーと境界条件をどのように処理すべきか。
- システムはどのような構成と責務に分けられるか。
- データはどのようなルールで保存され、変更されるか。
- 外部インターフェースとは何であり、どのような契約に従うか。
- どこに、どのようにデプロイし、運用するか。
- どの技術を使用し、なぜそれを選択したのか。
- 実装結果が要件と一致していることを、どのように検証するか。

プロジェクト文書がこれらの質問に対して一貫性があり検証可能な回答を提供し、実装者に重要な設計上の裁量が残されていない状態を、**Haetdachyeoの完了状態**と定義します。
